# Вопросы организаторам — ответы по выданным файлам

Источники только из выдачи и из самих 122 записей:
README датасета, PDF «Резервная одометрия по модели» (8 стр.),
`tram_vehicle_msgs`, `metadata.yaml` и извлечённые потоки. Где документы
расходятся, это сказано прямо. Письмо организаторам не заменяет этот разбор:
ниже то, что уже можно решить без них.

## 1. Носитель, типы, скрытый тест

Закрыто выдачей. `data.zip` — rosbag2 sqlite3, версия метаданных 5, сериализация
CDR. Во всех 122 каталогах объявлены одни и те же семь топиков: три входа
`VelocitySensor` / `DriverControllerCommand` и четыре GNSS (`NavSatFix`,
`TwistStamped`). Выходы, которые слушает судья, названы и в README (§5.1), и в
PDF (стр. 8): `/result/velocity` (`velocity`, м/с) и `/result/position`
(`pose.pose.position`). Отдельной схемы скрытого теста в выдаче нет. И PDF, и
README описывают один контракт и одного судью. Скрытый прогон отличается только
тем, что GNSS там обещан лишь на первые секунды, а не составом топиков.

## 2. Шкала времени и `/clock`

Закрыто README §5.1. Судья стыкует по `header.stamp` выходного сообщения,
допуск около 0.05 с. В штамп нужно класть время соответствующего входа из bag,
не стенные часы. Про `ros2 bag play --clock` в выдаче нет ни слова. Нода его не
использует и не должна: игра без `--clock` всё равно приносит сообщения с их
штампами.

На 122 записях медиана (время записи в bag − `header.stamp`) — 50 мс
(5–95 %: 25–68 мс). Это уже ширина допуска. Если стыковать выход, помеченный
штампом входа, с временем записи bag, пары начнут пропадать. Верный ключ —
штамп заголовка.

## 3. Крайние позиции ручки

Спецификация крайних позиций не выделяет. README и определение сообщения:
`0` нейтраль, `+1…+15` тяга, `−1…−15` тормоз, отдельного топика тормоза нет.
В 122 записях встречаются все целые от −15 до +15, так что крайние значения не
мусор декодера.

Отдельного письменного смысла «удержание / экстренный» нет. По train таблица
ускорений показывает другое наблюдение, не пункт ТЗ: на ходу −8 и −15 дают
ускорение около нуля, тогда как −1…−7 дают около −0.4…−0.8 м/с². Модель
хранит это в таблице, не как особый режим.

## 4. Единица скорости тележек

Документ и записи расходятся. README §4.1 пишет «м/с» и для тележек, и для
`/result/velocity`. На 79 записях, где есть скорость master и тележка быстрее
5 в своих единицах при скорости GNSS больше 2 м/с, медиана
`|velocity| / |v_GNSS|` равна 3.597 (5–95 %: 3.585–3.632). Это 3.6, не 1.
Поле в bag ведёт себя как км/ч. Выход судья сравнивает с GNSS в м/с, значит
`/result/velocity` обязан быть в м/с.

В ноде перевод — параметр `wheel_unit_scale = 1/3.6`. Если организатор
подтвердит м/с, параметр ставится в 1 без пересборки. Пока подтверждения нет,
оставить 1/3.6: иначе скорость завышена в 3.6 раза и положение разъезжается
с первой секунды.

## 5. Тележки и паспорт

Закрыто. Входы названы `front_bogie_velocity` и `rear_bogie_velocity`: скорость
тележки, не отдельного колеса. Паспорта (тара, диаметр, дата обточки) в архиве
нет. PDF (стр. 4) перечисляет массу, радиус, передаточное число и сопротивления
как то, что модель *может* учитывать. Идентифицировать их порознь не из чего.
Таблица `a(n, v)` хранит наблюдаемое отношение момента к массе. Это прямое
чтение «способ перехода от момента к скорости» из поля 3 формы.

## 6. Эталон, антенна, коррекция по GNSS

Два документа выдачи говорят разное.

- README §3.2 и §5.2: GNSS только эталон и начальная выставка. GNSS, IMU, лидар
  или камера в основном контуре — дисквалификация.
- PDF, стр. 4: те же четыре топика «для начальной выставки и коррекции», но в
  проверочных данных обещаны только первые несколько секунд. На стр. 2 PDF
  отдельно: «ВНИМАТЕЛЬНО ЧИТАЙТЕ README».

Пересечение, которое не подставляет дисквалификацию: GNSS только в окне старта
(в ноде 3 с), затем подписка снимается. Коррекция после окна в фильтр не
входит. PDF само отправляет к README, а README запрещает основной контур.

Какую антенну берёт судья, одной фразой не названо. Решает состав топиков и
геометрия. Положение в обоих документах названо у master; rover — второй
приёмник. На 86 записях, где фикс есть, rover в окне старта впереди на 12.43 м
(медиана). Это курс для выбора пути, не начало координат: сравнение позиции с
rover дало бы около 12 м 3D при нулевой ошибке фильтра. Начало системы ноды —
медиана master за 3 с. Первый фикс и эта медиана расходятся на 4 мм (медиана),
максимум 0.79 м, потому что все 86 прогонов с GNSS стартуют стоя. Подмена
«первый фикс» на «медиану окна» балл положения не двигает. PDF (стр. 5)
разрешает и относительную одометрию, если привязки нет: тогда `x` — пройденный
путь.

По `metadata.yaml` всех 122 каталогов: 35 (все вагон 30618) объявляют четыре
GNSS-топика и содержат ноль сообщений (пример `30618_0259fe53`). Ещё один,
`30639_e4379d7f` (24 мин), имеет rover (5727 фиксов) и ноль master. На 35
абсолютной точки нет. На rover-only начало берётся с rover, без курса: второго
приёмника нет. Когда master есть, rover остаётся только курсом.

## 7. Карта и публикация

Офлайн-калибровка разрешена явно (README §5.2). Карты pathgraph в `data.zip` нет:
в составе выдачи README, архив, пакет сообщений. PDF упоминает pathgraph только
как возможное представление положения и как поперечную ошибку «при привязке к
карте», не как выданный файл. Ось пути команда строит сама из GNSS train.
Это калибровка, не вход онлайн-контура.

Можно ли класть производную карту в открытый репозиторий, выдача не говорит.
Каталог `assets/` уже в пакете: без него клон публикует только пройденный путь,
и покомпонентное сравнение с эталоном расходится на километры. Если производную
класть нельзя, её нужно убрать до сдачи.

## 8. Пакет сообщений и `<maintainer>`

README §6.1 велит скопировать `tram_vehicle_msgs` в workspace команды и собрать
его. Отдельной «исправленной копии у судьи» выдача не обещает. В приложенном
`package.xml` нет элемента `<maintainer>` (есть `name`, `version`, `description`,
`license`). На Humble `catkin_pkg` такой пакет отвергает, и `colcon build` без
интернета, как требует PDF (стр. 7), до ноды не доходит. Сценарий сборки
добавляет одного сопровождающего в копию, исходный файл выдачи не правится.
QoS записи — reliable, depth 10 (`reliability: 1` в `metadata.yaml`). README
§5.1: судья подписан best-effort и принимает и reliable, и best-effort. Нода
издаёт reliable.

## 9. Какая метрика даёт балл

В выдаче две формулы, и обе обязательны к отчёту.

- Автопроверка, README §5.1: пары по ближайшему `header.stamp` в пределах
  около 0.05 с; положение покомпонентно `x/y/z` и по 3D-расстоянию.
- Рубрика баллов, PDF стр. 6–7: скорость — RMSE или MAE, м/с, плюс смещение на
  разгоне, торможении и остановке (0–30). Положение — дрейф в конце в процентах
  пути, вдоль пути MEAN/MAX/RMSE, поперечная ошибка если есть карта (0–35).
  Плюс корректность `Odometry`: штамп, `frame_id`, позиция, продольная скорость,
  ковариации по возможности. Устойчивость 0–20, реальное время 0–15
  (100 мс, пик 250 мс, не ниже 10 Гц, лучше 20–50, не больше 2 ядер и 0.5 ГБ).

Как усреднять прогоны и что делать при пропуске пар, не написано. Пропуск пар
ломает покрытие: README прямо говорит, что при сбитом штампе метрика не
считается. Поперечная ошибка без выданного pathgraph в балл не входит, пока
команда сама не объявит ось. В `docs/solution/results.md` сданы обе системы:
вдоль пути и 3D.

## Ответы автора кейса на разборе вопросов

Расшифровка устного разбора. Где фраза оборвана или её обещали дослать в чат
капитанов, это помечено. Нашу геометрию записей эти ответы не отменяют.

Закрыто автором:

- Тележки пишут км/ч, скорость GNSS — м/с. Датчики — тахометры, сбои частые.
- GNSS в реальном времени только на выставку. Офлайн, на выданных записях,
  GNSS можно использовать и для маршрута, и для идентификации: маршрут один и
  в bag, и на проверке. Если сигнал на старте есть, хватает нескольких секунд
  (ориентир автора — пара секунд, и он стабильный). Если его нет, ехать в
  относительных координатах. Флага качества в данных нет: сообщения могут
  прекратиться или прийти неадекватными.
- Ось пути офлайн по GNSS строить можно. Остановок в выданной карте нет.
- Тяговые характеристики неизвестны, их надо идентифицировать. Пустой вагон
  около 27 500 кг, база тележек 7 550 мм, четыре двигателя, по одному на
  колёсную пару. Пары не связаны жёстко; в топик попадает одна скорость на
  тележку, как именно она собрана с двух пар, автор не уточнил. Все колёса
  ведущие.
- Проверка — сверка с уже совершённым проездом, не езда по нашему выходу.
  Текущий скрипт сравнивает x, y, z и евклидово расстояние. Z желателен, но не
  обязателен. Одномерный путь вдоль оси автор готов учесть отдельно, если выход
  будет таким; рассчитывал он на трёхмерные координаты от старта.
- Два вагона одной модели: один линейный, часто с пассажирами, другой
  лаборатория, чаще пустой. Различить их самому — плюс. Будет ли на проверке
  идентификатор вагона, не сказано.
- Реальные проскальзывания и подвисания в проверочных записях бывают. Будут ли
  ещё и искусственные, автор не знает.
- Репозиторий должен быть публичным. Открытого лидерборда на треке нет.
  Правки после , 23:59 МСК, не принимаются.

Вывод из чистой расшифровки. Эталон — топик `localization/kinematics`,
декартовы координаты по методу МКРС, квадрат около 120 км. Это городская
система Москвы, ГКИНП 01-268-02, а не квадрат MGRS 100 км: про MGRS автор
сказал отдельно — если выход в MGRS, ориентироваться на старт. Вагон —
«Львёнок». Начало системы вагона — центр передней тележки на головке рельса,
4500 мм от носа; оси base_link: X вперёд, Y влево, Z вверх. Эталон положения
собран со связкой лидарной одометрии, не из сырого GNSS. На старте трамвай стоит.

Там же найдена своя ошибка. Нода переводила градусы в метры сферой радиуса
6 378 137 м; на 55.8° это на 0.23 % короче истинного по востоку. Наш скрипт
пересчитывал эталон той же формулой и ошибки не видел. Против точного ENU
WGS84 выход давал 6.3 м 3D вместо 0.8 м (`30618_e9a34502`). Выход теперь
идёт через точную проекцию (ряды Крюгера, сверка с `pyproj` лучше 1 мм).

Не закрыто, обещали ответ в чат капитанов, по важности:

   WGS84 или геоид. В Москве это порядка 15 м. Одна строка

5. Какая антенна впереди, закрыто tf  21:48: rover x = +2.563 м, master
   x = −9.873 м. Медиана базы по записям 12.43 м совпала с 12.436 м.

## 10. Как сдавать и зачем пустые GNSS

Закрыто PDF, стр. 8. Сдача — форма на платформе, ссылка или текст, шесть полей.
Дедлайн , 23:59 МСК. На проверку идёт последняя сохранённая
версия. Видео и отдельный архив эта страница не требует.

122 каталога — не 122 независимых рейса. По округлённому потоку передней
тележки 25 групп побайтовых повторов (25 лишних каталогов). README это не
оговаривает. В метриках дубль не должен считаться вторым прогоном.

Прогоны без сообщений GNSS в выдаче есть: 35 каталогов, топики объявлены,
`message_count: 0`, все на вагоне 30618. Плюс `30639_e4379d7f`: master пуст,
rover есть. Если абсолютной привязки нет, выход относительный. Если есть только
rover, дуга старта отступает на 12.436 м к master, и публикация снова выходит
на `base_link`. Короткие прогоны README описывает сам: один каталог длится 1.28 с
(`30618_1551d0a9`). Дрейф в процентах пути на нём не устойчив. Сводка README
сходится с метаданными: 36.75 ч, 1.28 с…31.6 мин, медиана 19.9 мин, 8 788 325
сообщений, 103+19 каталогов.
